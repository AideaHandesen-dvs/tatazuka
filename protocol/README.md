# 佇か protocol v0

server と client（および将来の connectors）の契約書。
**プロトコル変更は必ず両側を同じセッションで直す。片側だけのその場調整は禁止**（CLAUDE.md 参照）。

これも README.md 同様「育てていく」文書。決定済みの節と検討中（TBD）の節が混在する。

---

## 1. トランスポート【決定】

- WebSocket、**テキストフレームの JSON のみ**。バイナリフレームは使わない。
- 1 フレーム＝1 メッセージ。
- client は server が静的配信する（オリジン一つ、`ws://` / `wss://` は同一ホスト）。

## 2. メッセージの封筒【決定】

すべてのメッセージは次の形をとる：

```json
{"type": "<メッセージ型名>", "data": { ... }}
```

- `type`: メッセージ型名（小文字スネークケース）。
- `data`: 型ごとの payload。**封筒レベルのフィールドは増やせるが、payload はすべて `data` の中**。
- プロトコルバージョンは毎メッセージには持たせない。接続時の `hello`（§3）で一度だけ交換する。
- メッセージ ID・相関 ID は v0 には無い。必要になった型にだけ封筒レベルで足す（封筒/中身が分離しているので衝突しない）。

### 設計理由

佇か本体は将来 OpenCLAW 等との**仲介ハブ**になる（README §4）。ハブの仕事は「封筒を見てルーティングし、中身は開けずに転送」であり、封筒と payload の境界を構造で保証する type+data 分離はその先払い。平坦な形（`{"type": "say", "text": ...}`）の方が軽くて手打ちしやすいが、A→B の移行は破壊的変更で参加者が増えるほど高くつくため、最初から B を採る（2026-06-08 決定）。

## 3. hello / capability ネゴシエーション【決定】

プログレッシブ・エンハンスメントの心臓部。

### 3-1. 接続の流れ

1. client が WS 接続し、**client から先に** `hello` を送る（cap を知っているのは client だから）。
2. server が `welcome` を返す。protocol バージョン不一致なら `error` を返して切断する（v0 は完全一致のみ）。
3. 以後、通常のメッセージ交換。

```json
// client → server（接続直後、一度だけ）
{"type": "hello", "data": {
  "protocol": 0,
  "label": "リビングのiPad",
  "caps": {"orientation": "ask", "motion": "ask", "camera": "none", "webgl": "on"}
}}

// server → client
{"type": "welcome", "data": {"protocol": 0}}
```

- `protocol`: 整数。バージョン交換は接続時のこの一回だけ（§2）。
- `label`: 端末の名前（任意）。複数端末の識別（§6）と、佇かが端末を呼び分ける演出に使う。
- `caps`: cap 名 → 状態のマップ。

### 3-2. cap は三値 — ライフサイクルを持つ

iOS の傾きセンサ等は**ユーザー操作起点の許可**が要るため、接続時点では「API がある」ことしか分からない。cap の値は bool ではなく三値：

| 値 | 意味 |
|---|---|
| `"none"` | API/ハードが無い。または許可をねだって拒否された |
| `"ask"` | API はあるが許可待ち（ユーザー操作起点の許可ゲート） |
| `"on"` | 許可済み・稼働中 |

`"ask"` を server に見せるのが肝で、これにより**佇か自身が許可をねだれる**（「なあ、傾けて覗き込んでみないか？」）。無機質な許可ダイアログをキャラの台詞に変える。実際の許可リクエストはユーザーのタップを起点に client が発行する。

- 拒否されたら `ask → none` に落とす。server は「もうねだらない」と判断できる。
- cap 初期セット：`orientation` / `motion` / `camera` / `webgl`（README §3-4）。
- ポインタ系入力（なでる・つつく）は全端末で取れるため cap に**含めない**。
- server は知らない cap 名を**黙って無視する**（前方互換）。

### 3-3. cap の変化は専用 `caps` メッセージ

`hello` は接続の儀式として一度きり。接続後に cap が変わったら（許可が下りた・カメラを切った等）、**差分だけ**を `caps` 型で送る：

```json
// ユーザーが許可ボタンを押して傾きが生きた
{"type": "caps", "data": {"orientation": "on"}}
```

## 4. server → client の語彙【決定】

### 4-1. 設計原則

- **意味論型**。server は「呆れてる」「こっちを見る」という**意味**を送り、描画の解釈は client に任せる。さくらスクリプトの `\s[5]`（演出指定型）は採らない——顔が差し替え可能（README §5）で端末ごとに描画力が違う以上、server が描画を握ると両方が壊れる。
- client は**解釈できない値を黙って無視してよい**。表情を全部無視しても佇かは成立する。プログレッシブ・エンハンスメントが語彙レベルまで貫通する。
- **「間」は server が刻む**。台詞の間・演技のタイミングは server 側のタイマーが管理し、client は受信即表示のバカでいられる（状態機械・再生エンジン不要）。LAN 前提なので遅延は無視できる。さくらスクリプト的な一括 script 送信は採らない。
- mood / act の値は**日本語文字列**（例 `"呆れ"`）。契約書も読み手も日本語なので翻訳で意味をぼやかさない。

### 4-2. メッセージ型

```json
// 台詞。mood は任意——付ければ台詞と表情が同時着地（アトミック）
{"type": "say", "data": {"text": "それ3時間やってるぞ", "mood": "呆れ"}}

// 無言の表情変化（ジトーっと見るだけ、とか）
{"type": "emote", "data": {"mood": "疑い"}}

// 動き
{"type": "motion", "data": {"act": "こっちを見る"}}
```

- 新しい `say` は前の台詞を置き換える。台詞を消すだけの指示は、必要になったら足す。

### 4-3. 語彙表（育てていく）

語彙表そのものが protocol の契約の一部。人格（M4）を作りながら増やす。

- `mood` 初期セット：`通常` / `呆れ` / `疑い` / `喜び` / `怒り` / `照れ`
- `act` 初期セット：`こっちを見る` / `うなずく` / `首を振る` / `跳ねる`

## 5. client → server の語彙【決定】

### 5-1. 設計原則

- **server は画面のどこに佇かが描かれているか知らない**（描画は client の仕事）。よって生の座標やセンサ値ではなく、client が解釈した**意味**を送る。§4 と対称。
- タッチもセンサも「**佇かが感じたこと**」として `sense` 型一本に集約し、`kind` で区別する。語彙追加＝`kind` の値追加であり、型表は不変。server のハンドラも一箇所にまとまる。

### 5-2. メッセージ型

```json
{"type": "sense", "data": {"kind": "つつく", "part": "頭"}}
{"type": "sense", "data": {"kind": "なでる", "part": "頭"}}
{"type": "sense", "data": {"kind": "揺らす"}}
```

- `part` はポインタ系のみ。当たり判定の領域分けは client（顔の実装）が持つが、部位名の語彙は契約の一部。
- **連続動作（なでなで）は一定量ごとのイベント繰り返し**で表す。なで続けている間、client は「一なで分」たまるたびに同じ `sense` を送る。server は回数を数えるだけで「なでられ続けてる」が分かる（伺かの mousemove カウント文化の直系）。開始/終了ペアは採らない——終了の取りこぼしで「永遠になでられてる」事故が出るから。
- **傾きの生データは v0 では server に流さない**。パララックス描画は client 内で完結する。加速度も意味化して `揺らす` 等だけ送る。スタックチャン連携（README §4）で生の傾きが必要になったら「tilt ストリーム」を別途設計して足す（非破壊的追加）。

### 5-3. 語彙表（育てていく）

- `kind` 初期セット——ポインタ系：`つつく` / `なでる` / `長押し`、センサ系：`揺らす` / `持ち上げる`
- `part` 初期セット：`頭` / `顔` / `体`

## 6. 再接続・複数端末【決定】

### 6-1. プレゼンス——端末＝部屋

佇かは原則**一度に一つの端末にしか居ない**。居ない端末は「誰もいない部屋」（カメラ背景の透明な箱だけがある）。つつくと隣の部屋から移動してくる。存在感は「どこにでも居る」ではなく「今ここに居る／居ない」から生まれる。

```json
// server → 各 client
{"type": "presence", "data": {"here": true}}
{"type": "presence", "data": {"here": false}}
```

- **「一度に一箇所」は server の人格側の方針であって、protocol の制約ではない**。debug モードの server が全部屋に `here: true` を出すのは契約違反ではない。
- v0 の server 実装は「全部屋に居る」の退化形（事実上のブロードキャスト）から始めた。**実装済み**：`server/hub.js` が本物の移動ロジック（occupant の選択・つつかれた空き部屋への移動・離脱時の移り先）を持つ。退化形は `TZ_BROADCAST=1` のフラグで残す（開発・デバッグ用）。**この成熟で wire 契約（`presence` メッセージ）は一切変わっていない**。
- どの部屋に居るか・いつ移動するかの決定はすべて server。client は `presence` に従って描くだけ。

### 6-2. 再接続

- 切断したら client は自動再接続し、**もう一度 `hello` からやり直す**。server は新規接続と同じ扱い（接続をまたぐ状態の引き継ぎ無し＝一番枯れる）。
- **切断中に発生した台詞・イベントは捨てる**。マスコットはメッセンジャーではない。見逃した茶々は見逃したでいい。
- 再接続後、server は現在の状態（mood・presence）を送り直して見た目を復元する。

### 6-3. 落ちたことへの「言及」——再送ではなく茶々

切断はエラーとして隠すのではなく、**人格の材料にする**（「おい、なんかエラーで今落ちたぞ」）。そのために：

```json
// 再接続時の hello。resumed = 「さっきまで繋がってた自覚がある」の申告
{"type": "hello", "data": {"protocol": 0, "label": "リビングのiPad",
                           "resumed": true, "caps": {...}}}
```

- client 側が落ちた／回線が切れた → client が `resumed: true` で申告し、server が茶々を入れられる。
- server 側が落ちた → 再起動後も `resumed: true` の hello が来るので「自分が落ちてた」ことに気づける。
- server は `label` ごとに最後に見た時刻を覚えてよい（「リビングのiPad、3分ぶりだな」）。これは server の内部実装であり protocol の関知事項ではない。**実装済み**：`server/reunion.js` が label→最終時刻を覚え、間隔が空いた再接続で `greet.reunion` として間隔に言及する。

### 6-4. 認証

v0 には**無い**。信頼できる LAN ＋ HTTPS 終端一箇所が前提。インターネットに出すときの認証・端末ペアリングは将来の protocol バージョンで扱う。
