# 佇か（たたずか）設計メモ

> 伺かのようなデスクトップマスコットを、現代的な形で作り直すプロジェクト。
> これは確定仕様ではなく、議論の到達点をまとめた「育てていく」設計メモ。

---

## 1. コンセプト

伺か（うかがか）の精神的後継。デスクトップに常駐し、人格を持ち、こちらに茶々を入れてくる存在。
ただし伺か本家の弱点（特にLinuxでの表示）を、アーキテクチャの根本的な見直しで回避する。

仮の名前は **「佇か（たたずか）」**。「佇む」から。静かにそこに居てくれる感じ。

### やりたいことの方向性（まだ確定ではない）

- デスクトップを動き回って仕事を邪魔してくる存在
- ただし**今は**デスクトップを操作する機能は持たせない（操作主体だと誤解されない設計にしたい）
- OpenCLAW インターフェース（スタックチャン的なもの）と接続しても楽しそう

---

## 2. 最大の技術的課題：Linuxでの透過表示

デスクトップに直接マスコットを住まわせる場合、Linuxでは背景透過が沼になる。

- **X11 か Wayland か**でまず分岐する。Wayland では「ウィンドウを好きな位置に置く・最前面固定・クリックスルー」というマスコットに必須の操作が、プロトコル上できない／コンポジタ独自拡張頼みになる。
- 透過自体が「コンポジタが合成してくれているか」に依存する。軽量WM・コンポジタ無効環境では背景が真っ黒になる。
- Java（Swing/JavaFX）等で書いても、per-pixel透過は環境差をモロに食らう。「書けるけど環境によっては透過しない」という一番タチの悪い状態になる。
- ディストリビューション対応・他OS対応を進めるほど、この環境差が増える。

### 結論：デスクトップに直接住まわせるのを諦める

これはLinux使いとしてむしろ正しい判断。表示を別の場所に逃がすことで、透過・コンポジタ・WMの問題が**すべて関係なくなる**。

---

## 3. 採用する方針：表示をスマホ／タブレットに逃がす

本体（佇かの「頭脳」）は Linux 上のサーバープロセスとして動かし、表示はブラウザを持つ別端末（スマホ・タブレット・サブモニタ・余った端末）が担当する。両者は WebSocket で繋ぐ。

この方針が単なる妥協ではなく**上位互換**になる理由が、議論の中で複数見つかった。

### 3-1. バックカメラによる「端末そのものの透過」

スマホ／タブレットのバックカメラ映像を表示の背面に流すと、**端末そのものが透明になったように見える**。AR的な「窓」になる。

- デスクトップ透過は「背景を消す」ことしかできないが、これは端末越しに机が見える状態を作れる。
- 佇かが本当に机の上に立っているように見える。
- 端末を動かせば視差で背景がズレるので実在感が出る。
- ブラウザの `getUserMedia` で撮れるので実装も標準的。

### 3-2. 表示先は「ブラウザが動けば何でもいい」

軽く・枯れた技術で表示クライアントを作れば、性能の低い端末でも住処にできる。
**中古の学習タブレット（チャレンジタッチ・スマイルゼミ等、数百〜数千円のジャンク）にすら表示可能**であることを、この設計の強みの証明にしたい。
「どこにでも憑ける」のは伺かのゴーストらしさとも噛み合う。

> 補足（2026-06）：初代の「中古500円チャレンジタッチ」は市場から枯れたが、スマイルゼミのジャンク（相場2千円前後、公式の Android 化手順あり）が同じポジションにいる。チャレンジパッド第6世代は公式に Android モードを積んだので、数年後にはこれがジャンクで流れてくる。**試金石は特定機種ではなく「数千円以下の中古学習タブレット」というクラス**。必要になった時に一番安い弾を拾う。

### 3-3. 傾きセンサで奥行きを出す

スマホ・タブレット・スタックチャンに入っている傾きセンサ（IMU）を表示に反映すれば、どこで表示してもリッチになる。

- ブラウザの `DeviceOrientation`（α/β/γ）を視点に使う。
- 端末を傾けると佇かを**見る角度が変わる**（パララックス／覗き込み）。
- バックカメラ背景も傾きで一緒に動かせば、**端末が透明な箱で、中に佇かが入っている**ように見える。
- スタックチャンに載せる場合は、スタックチャンのIMU傾きを「佇かが体を傾けた」表現に変換する逆向きの使い方もできる。

### 3-4. 表示端末の戦力図

**原則：cap（能力）で設計し、機種で設計しない。** protocol が知っていいのは「傾きが取れるか」「カメラがあるか」だけで、「iPad かどうか」ではない。デバイスは cap の束として扱う。

| 端末 | ポインタ | 傾き/加速度 | カメラ | GPU | 役割 |
|---|---|---|---|---|---|
| デスクトップブラウザ | マウス | ✗ | △ | ◎ | 開発基準・最低ラインの確認 |
| iPad Air 2（手持ち） | タッチ◎ | ✓（要許可） | ✓ | ○ | **フル体験のリファレンス** |
| Nexus 7 Linux化（手持ち） | タッチ | おそらく✗ | ？ | △ | **欠損 cap の試金石** |
| 中古学習タブレット（将来） | タッチ | ✗ | ✗ | ✗に近い | 最底辺の証明 |

リッチ側のリファレンス（iPad）と欠損側の試金石（Nexus 7）が両方手元にあるので、買い物ゼロで設計検証が回る。

入力は2種類に分かれ、protocol 上の扱いが違う：

- **ポインタ系（なでる・つつく・長押し）→ cap 交渉不要**。Pointer Events はタッチでもマウスでも同じ API。デスクトップでもマウスで佇かをなでれる。「なでなで」をタッチ端末の特権にしない。
- **センサ系（傾き・加速度・カメラ）→ cap 交渉が必要**。ハードの有無＋許可ゲートがあるため、接続時に名乗る対象。

加速度（`DeviceMotion`）は傾きと別の語彙。**デスクトップモニタはデカくて揺らさないから不要。タブレットは小さくて持って動かすから、読めば表現が広がる**（「揺らす」「持ち上げる」の検出 →「おい、揺らすな」と怒る佇か）。机に置けば視点固定、持ち上げれば覗き込み＋揺れ検出、という端末の使われ方の差がそのまま体験の差になる。

cap の初期セット案：`orientation` / `motion` / `camera` / `webgl`（ポインタは交渉不要なので含めない）。

## 4. アーキテクチャ

```
表示クライアント（ブラウザ / どんな端末でも）
  ├ getUserMedia      → バックカメラを背景に（端末の透過演出）
  ├ DeviceOrientation → 傾きで視点を動かす（覗き込める奥行き）
  ├ 軽量2.5D/3Dで佇かを描く（顔の作り込みは後で差し替え可能）
  └ WebSocket で本体と繋がる
        ▲
        │ WebSocket / HTTP
        ▼
本体（Linux デーモン）
  ├ 状態・人格・イベント処理（時刻 / 天気 / 通知など）
  ├ WebSocket サーバー
  └ （将来）OpenCLAW 等への接続口
```

### OpenCLAW / スタックチャン連携

スタックチャンの本質は「顔（表示）」と「中身（制御）」が分離していて、API経由で喋らせたり動かしたりできること。
佇か本体を**仲介ハブ**にすれば、表示先を差し替え可能にできる。

```
OpenCLAW  ⇄  佇か本体  ⇄  表示クライアント（ブラウザ / 物理スタックチャン）
```

これにより、表示が物理スタックチャンでもブラウザでも同じ本体で扱える。

### 「仕事を邪魔してくる」案との両立

表示をスマホ／タブレットに逃がした佇かが、PC作業中に
「おい、休憩しろ」「それ3時間やってるぞ」とスマホ側から茶々を入れてくる、という形。
デスクトップを占有しないぶん、邪魔のクオリティそのものに集中できる。今っぽくて実害もない。

## 5. 「顔」の方向性（保留中）

最初はミニマルかリッチかで迷っていたが、傾きセンサを使うなら論点が変わる。

- 重要なのはミニマル／リッチではなく、**3D的な見え方をするか**。
- 傾けて覗き込めるなら、目と口だけのミニマルな顔でも一気にリッチに見える。
- Live2D は平面前提なので傾きとの相性はそこそこ。
- **軽量3D（Three.js の板ポリ多層 = 2.5D、または簡易3Dモデル）** が、傾きセンサ・カメラ透過・低性能端末対応の3つすべてに効く中心になりそう。

→ 顔のデザインは仮のままでよい。差し替え可能にしておく。

---

## 6. 技術的に握っておくべき現実（制約）

- `DeviceOrientation` と `getUserMedia` は両方とも **HTTPS（または localhost）でないとブラウザが許可しない**。
- iOS は傾きセンサに**明示的な許可リクエスト（ユーザー操作起点）**が必要。
- **自己署名証明書は iOS が特に痛い**（プロファイルのインストール＋信頼設定まで必要）。HTTPS 配信方法は iPad を基準に決めること。
- 中古学習タブレットのような端末は、そもそもセンサやカメラAPIが載っていない可能性がある。

### 対策：機能は段階的にオンになる作りにする（プログレッシブ・エンハンスメント）

全端末でフル機能を前提にしない。使える機能だけが順に有効化される設計にする。

- 傾きが無ければ → 覗き込み無効
- カメラが無ければ → 背景は単色
- それでも → 佇かは出る

## 7. 最初のプロトタイプ候補

一番テンションが上がるのは
**「傾けると覗き込める＋背景がカメラ抜き」の表示クライアントの素**。

顔が仮でも、端末を傾けた瞬間に「これ箱の中にいる」と体感できれば、方向性が確信に変わる。

> 【2026-06-08 達成】実機 iPad Air 2（iOS 12.5.8）で、傾き覗き込み＋カメラ背景による「透明な箱の中に佇かがいる」体感を確認。仮の顔（CSS 3D の卵）でも成立した。最も古い標的端末で動いたことで、プログレッシブ・エンハンスメントの設計が実証された。

## 8. リポジトリ構成

```
tatazuka/
├── README.md      ← この設計メモ（育てていく）
├── server/        ← 本体デーモン（WSサーバー＋人格＋イベント処理）
├── client/        ← 表示クライアント（静的ファイル。server が配信する）
├── protocol/      ← WS メッセージ仕様。server と client の契約書
└── connectors/    ← 将来の openclaw/ など外部接続
```

- **client は server が配信する**。オリジンが一つになり、HTTPS 終端も一箇所で済む。表示端末は「URLを開くだけ」。
- **`protocol/` が設計の中心**。プログレッシブ・エンハンスメント（capability ネゴシエーション）はここに書く。
- プロトコル変更は必ず server / client の両側に波及する。**片側だけのその場修正は禁止**。
- 将来 systemd user サービス化する前提なので、`tatazuka` という名前と `server/` の位置は**改名禁止**。
