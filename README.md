# 佇か（たたずか）

> 伺（うかが）かの精神的後継デスクトップマスコット。
> Linux デスクトップ透過の沼を**捨て**、表示をブラウザ端末（スマホ・タブレット・余った端末）に逃がす。
> 端末のバックカメラを背景に流し、傾けると覗き込める——**「透明な箱の中に佇かがいる」**。

「佇む」から。静かにそこに居て、ときどき茶々を入れてくる存在。

---

## 動くもの（現状）

一日で骨組みからここまで動いている（2026-06-08 時点）：

- **VRM アバターが立つ** — Android Chrome 等の WebGL 端末で VRM の佇かが表示され、端末を傾けると**目がこちらを追う**（視線追従）。実機確認済み。
- **古い端末でも必ず出る** — iPad Air 2（iOS 12.5.8）のような古い端末は CSS で描いた簡易な顔にフォールバック。実機で「箱の中にいる」体感を確認済み。
- **本体が喋る** — 依存ゼロ（node 標準のみ）の WebSocket サーバーが、時刻帯や在席時間を見て「それ3時間やってるぞ。休憩しろって」と茶々を入れる。
- **契約が両側で実装済み** — client と server の通信仕様 protocol v0 が、両側の実コードで裏付けられている。

**喋る言葉も差し替えられる** — 「何を喋るか」を LLM 生成に格上げできる（ollama / Claude API 両対応）。
人格そのもの（ゴースト）も `characters/<名前>.txt` で丸ごと差し替えられる（伺かの ghost 文化）。
LLM が無くても・遅くても佇かは手書きの台詞で喋る（[server/README.md](server/README.md) の「LLM persona」）。
**天気にも反応する** — 都市を設定すると、雨の降り始めや暑さ寒さに茶々を入れる（Open-Meteo・キー不要）。
**作業も見ている** — 同じ PC 上で動くので、長く席を外すと「どこ行った」、戻ると気づく（idle 検知・X11/Wayland）。
**家の状態にも反応する** — Home Assistant と繋ぐと、帰宅すれば「おかえり」、外出すれば「いってらっしゃい」（connectors/ の入力役・在席判定・PE）。
**一度に一箇所にしか居ない** — 複数端末を繋いでも佇かは一つの部屋にだけ居て、空いた端末を つつくと そっちへ移ってくる（仲介ハブ・[server/README.md](server/README.md) の「プレゼンス」）。物理スタックチャンも将来この同じハブに挿さる「もう一つの身体」になる。
**戻ると覚えている** — 端末ごとに最後に見た時刻を覚えていて、しばらくぶりに開くと「居間、3分ぶりだな」と茶々を入れる。
次の一手：connectors の「出力」側 —— 物理スタックチャンを表示先にする（[connectors/](connectors/README.md)・要実機）。

## クイックスタート

依存パッケージは無い（`npm install` 不要）。要るのは Node.js と、HTTPS のための証明書だけ。

```sh
# 1) 証明書（初回だけ）。getUserMedia / DeviceOrientation は HTTPS 必須なので要る。
#    <LAN-IP> は表示端末から届くこのマシンの IP（例: 192.168.0.5 など）。
mkcert -install
mkcert -cert-file server/certs/cert.pem -key-file server/certs/key.pem \
  "$(hostname)" localhost 127.0.0.1 <LAN-IP>

# 2) 起動（HTTPS 静的配信 ＋ WebSocket。依存ゼロ）
node server/serve.js

# 3) 表示端末（スマホ等）のブラウザで開く
#    → https://<LAN-IP>:8443/?label=好きな名前
```

- **表示端末に mkcert の root CA を信頼させる**初回作業が要る（iOS / Android で手順が違う）。→ [server/README.md](server/README.md)
- **VRM アバターを出すには** `.vrm` を `client/models/` に置く（無ければ CSS の簡易顔になる）。→ [client/README.md](client/README.md)

# 設計の記録（なぜこの形か）

> ここから下は「育てていく設計メモ」。確定仕様ではなく、議論の到達点と**なぜそう決めたか**の記録。
> 設計の全体像はここを参照する（CLAUDE.md の規約）。

## 1. コンセプト

伺かの精神的後継。デスクトップに常駐し、人格を持ち、こちらに茶々を入れてくる存在。
ただし伺か本家の弱点（特に Linux での表示）を、アーキテクチャの根本的な見直しで回避する。

- デスクトップを動き回って仕事を邪魔してくる存在。
- ただし**今は**デスクトップを操作する機能は持たせない（操作主体だと誤解されない設計にしたい）。
- OpenCLAW インターフェース（スタックチャン的なもの）と接続しても楽しそう。

## 2. 最大の技術的課題：Linux での透過表示 → 諦めた

デスクトップに直接マスコットを住まわせる場合、Linux では背景透過が沼になる。

- **X11 か Wayland か**でまず分岐する。Wayland では「ウィンドウを好きな位置に置く・最前面固定・クリックスルー」というマスコットに必須の操作が、プロトコル上できない／コンポジタ独自拡張頼みになる。
- 透過自体が「コンポジタが合成してくれているか」に依存する。軽量 WM・コンポジタ無効環境では背景が真っ黒になる。
- Java（Swing/JavaFX）等で書いても、per-pixel 透過は環境差をモロに食らう。「書けるけど環境によっては透過しない」という一番タチの悪い状態になる。
- ディストリビューション対応・他 OS 対応を進めるほど、この環境差が増える。

**結論：デスクトップに直接住まわせるのを諦める。** 表示を別の場所に逃がすことで、透過・コンポジタ・WM の問題が**すべて関係なくなる**。これは妥協ではなく上位互換である（次節）。

## 3. 採用した方針：表示をスマホ／タブレットに逃がす

本体（佇かの「頭脳」）は Linux 上のサーバープロセスとして動かし、表示はブラウザを持つ別端末が担当する。両者は WebSocket で繋ぐ。これが上位互換になる理由：

### 3-1. バックカメラによる「端末そのものの透過」

スマホ／タブレットのバックカメラ映像を表示の背面に流すと、**端末そのものが透明になったように見える**。AR 的な「窓」になる。

- デスクトップ透過は「背景を消す」ことしかできないが、これは端末越しに机が見える状態を作れる。
- 佇かが本当に机の上に立っているように見える。端末を動かせば視差で背景がズレるので実在感が出る。
- ブラウザの `getUserMedia` で撮れるので実装も標準的。

### 3-2. 表示先は「ブラウザが動けば何でもいい」

軽く・枯れた技術で表示クライアントを作れば、性能の低い端末でも住処にできる。
**中古の学習タブレット（チャレンジタッチ・スマイルゼミ等、数百〜数千円のジャンク）にすら表示可能**であることを、この設計の強みの証明にしたい。「どこにでも憑ける」のは伺かのゴーストらしさとも噛み合う。

> 補足（2026-06）：初代の「中古500円チャレンジタッチ」は市場から枯れたが、スマイルゼミのジャンク（相場2千円前後、公式の Android 化手順あり）が同じポジションにいる。**試金石は特定機種ではなく「数千円以下の中古学習タブレット」というクラス**。

### 3-3. 傾きセンサで奥行きを出す

スマホ・タブレットの傾きセンサ（IMU）を表示に反映すれば、どこで表示してもリッチになる。

- ブラウザの `DeviceOrientation`（α/β/γ）を視点に使う。端末を傾けると佇かを**見る角度が変わる**。
- バックカメラ背景も傾きで一緒に動かせば、**端末が透明な箱で、中に佇かが入っている**ように見える。
- スタックチャンに載せる場合は、IMU 傾きを「佇かが体を傾けた」表現に変換する逆向きの使い方もできる。

### 3-4. cap（能力）で設計し、機種で設計しない

protocol が知っていいのは「傾きが取れるか」「カメラがあるか」だけで、「iPad かどうか」ではない。デバイスは cap の束として扱う。

| 端末 | ポインタ | 傾き/加速度 | カメラ | GPU | 役割 |
|---|---|---|---|---|---|
| デスクトップブラウザ | マウス | ✗ | △ | ◎ | 開発基準・最低ラインの確認 |
| Android スマホ | タッチ | ✓ | ✓ | ○ | **VRM フル体験の主力** |
| iPad Air 2（iOS 12.5.8） | タッチ | ✓（要許可） | ✓ | △ | 古い端末の試金石（CSS 顔） |
| 中古学習タブレット（将来） | タッチ | ✗ | ✗ | ✗に近い | 最底辺の証明 |

入力は2種類に分かれ、protocol 上の扱いが違う：

- **ポインタ系（なでる・つつく・長押し）→ cap 交渉不要**。タッチでもマウスでも同じ。「なでなで」をタッチ端末の特権にしない。
- **センサ系（傾き・加速度・カメラ）→ cap 交渉が必要**。ハードの有無＋許可ゲートがあるため、接続時に名乗る。

加速度（`DeviceMotion`）は傾きと別の語彙。**デスクトップモニタはデカくて揺らさないから不要。タブレットは小さくて持って動かすから、読めば表現が広がる**（「揺らすな」と怒る佇か）。

cap の初期セット：`orientation` / `motion` / `camera` / `webgl`（ポインタは交渉不要なので含めない）。

## 4. 顔：軽量3D（VRM）を上位レイヤで

傾けて覗き込めるなら、重要なのはミニマル／リッチではなく**3D 的な見え方をするか**。軽量3D が、傾きセンサ・カメラ透過・低性能端末対応のすべてに効く。

採用形：**CSS の簡易な顔を「床」として常に持ち、WebGL が効く端末ではそこに VRM アバターを「格上げ」で載せる**。顔のレベルでもプログレッシブ・エンハンスメント（§5）。VRM は three.js + three-vrm を vendor 同梱（バンドラ不要・外部 CDN 非依存）。視線追従（覗き込むと目で見返す）入り。モデル（.vrm）は各自で `client/models/` に置く（git 管理外）。詳細は [client/README.md](client/README.md)。

→ 顔のデザインは差し替え可能。`client/face.js`（CSS）/ `client/face-vrm.js`（VRM）を入れ替えれば変わる。

## 5. プログレッシブ・エンハンスメント（背骨）

`DeviceOrientation` と `getUserMedia` は HTTPS 必須・iOS は明示許可が要る・古い端末はセンサや新しい JS が無い——という現実がある。だから**全端末でフル機能を前提にしない。使える機能だけが順に有効化される**設計にする。

- WebGL が効かない → CSS の簡易な顔
- 傾きが無い → 覗き込み無効
- カメラが無い → 背景は単色
- それでも → **佇かは出る**

この背骨は実装の隅々まで貫通している（cap 三値・顔の格上げ・人格層の LLM 後付け・iOS 12 対応）。

## 6. 人格層：いつ喋るか・何を喋るか・誰が喋るか

佇かの「らしさ」は server 側の人格層が作る。ここも顔と同じく**差し替えと格上げ**で設計する。詳細仕様は [server/README.md](server/README.md)、ここは「なぜこの形か」。

### 6-1. behavior と persona を分ける

- **behavior（いつ・どんな状況で喋るか）** … トリガ・間・presence の副作用。protocol v0 の server 側。
- **persona（何を喋るか）** … situation タグ（`greet` / `work.180` / `weather.rain.start` …）→ `{text, mood}`。

台詞生成を **`line(situation, ctx)` 一点の継ぎ目**に閉じ込めた。behavior は「何を」を知らない。これで「何を喋るか」だけを丸ごと差し替えられる。

### 6-2. 人格層もプログレッシブ・エンハンスメント

ルールベースの手書き表が**床**。LLM persona が**格上げ**（環境系の台詞を生成に置き換える。反応系の即レスは手書きのまま）。**LLM が無くても・遅くても・壊れても佇かは喋る**（同じ `line()` の顔で、失敗時はルール表へ）。卵 → VRM と同じ発想を人格でやる。provider は ollama（ローカル・無料）/ Claude API の両対応。

### 6-3. ゴースト：人格は差し替えられるデータ

伺かの「ゴースト」文化を引く。**キャラ（誰か＝`characters/<名前>.txt`）** と **出力契約（tatazuka 固定の JSON/mood ルール）** を分離。**ベースモデルにはキャラを焼かない**——汎用エンジンのまま、キャラは実行時の system プロンプトに合成する。だから `TZ_CHARACTER` を変えれば別ゴーストに丸ごと差し替わる（同梱：佇か・執事・妹・化け猫・式神）。小型モデルでは **system をキャラ専用にし、出力契約は生成直前に置く**とキャラ忠実度が上がる（厚いゴーストほど顕著＝表現の頭打ちを緩める）。同梱5体は人間（執事・妹）／物の怪（化け猫）／無機質（式神）まで振れ、**同じ顔・同じ JSON 契約のまま声色だけ丸ごと変わる**ことを示す（絵師いらず＝テキスト1枚でゴーストが増える）。小型モデル特有の崩れ——`照れ` への mood 偏り・`／` で言い回しを並べ続ける run-on（敬語ゴーストの尻切れの主因）・`text` への mood 漏れ——は **実測で詰めた**（数値と手当ては [server/README.md](server/README.md) の「LLM persona」）。

### 6-4. イベント源パターン：外部の出来事を situation に翻訳する

「いつ喋るか」の蛇口を増やす共通の型。**外部イベント源 → situation タグ → 人格層**。各イベント源は:

- **protocol を変えない**（`say` に乗るだけ。client は無改修）。
- **PE で縮退**（取れなければ黙る。佇かは他の理由で喋る）。
- **IO を注入してテスト**（時計・fetch・コマンド実行を差し替え可能に）。

この型で実装済み：①触られた（sense）②時刻帯 ③在席・連続時間 ④**天気**（Open-Meteo・キー不要、雨の降り始めや暑さ寒さ）⑤**作業監視**（ホストの入力 idle で離席/復帰、X11/Wayland）⑥**Home Assistant**（在宅/外出。connectors/ の入力役の初例）⑦**git**（監視リポの未コミット clean↔dirty ＋未 push unpushed↔pushed。soft 委譲の readonly プローブ初例＝§7-1）⑧**ディスク**（空き容量の low↔ok。`df` をしきい値で見る・readonly）⑨**メモリ**（空きメモリの low↔ok。`/proc/meminfo`・デバウンス付きしきい値）⑩**ネット**（オンライン/オフライン。`/sys/class/net`・二値）⑪**通信レート**（busy↔idle。`/proc/net/dev` の累計を差分してレート化・しきい値）⑫**バッテリー**（残量の low↔ok ＋満充電ケア。`/sys/class/power_supply`・**放電中だけ**警告するゲート付きしきい値＝ノート利用者全員に効く）⑬**温度**（hot↔ok。`/sys/class/thermal`・膝が熱い／ファンが唸る）⑭**ダウンロード完了**（`~/Downloads` の差分・**エッジ型**＝「何か来たぞ」・件数のみ）⑮**ゴミ箱**（溜まったら掃除を促す。件数しきい値）⑯**スリープ復帰**（poll の空白で「おかえり」＝ファイルすら読まない時計だけの型）。⑫以降は **git/CI のような開発者ニッチでなく、コンピュータを触る大多数に効く readonly** を優先した群。④以降は同じ `sources` の蛇口に挿さる（behavior.js は出自を知らない）。connectors の設計は §7。

## 7. 仲介ハブ構想（connectors）

スタックチャンの本質は「顔（表示）」と「中身（制御）」が分離していて API 経由で動かせること。佇か本体を**仲介ハブ**にすれば、表示先を差し替え可能にできる。

```
OpenCLAW  ⇄  佇か本体  ⇄  表示クライアント（ブラウザ / 物理スタックチャン）
```

protocol の封筒を `{type, data}` に分離してあるのは、この「封筒を見て中身を開けずに転送する」ハブの仕事への先払い（[protocol/README.md](protocol/README.md) §2）。

connector は二つの顔を持ち、**どちらの契約も既存の決定が先に定義済み**——「入力」（外の出来事 → situation。§6-4 のイベント源パターン）と「出力」（佇かの語彙を別の身体で再生。封筒分離＋意味論型語彙 §4-1 で物理スタックチャンは「v0 を喋るもう一つの client」になる）。connectors/ は新 protocol を発明せず、第三者アダプタの置き場にとどまる。詳細と土台は [connectors/README.md](connectors/README.md)。

### 7-1. OpenClaw 連携：佇か＝指揮役 × soft 委譲 — soft は「ランタイム無し」で閉じる【決定・2026-06-09】

§7 の図で `OpenCLAW` を「表示先（身体）」のように描いてきたが、これは**誤った見立て**だった。OpenClaw（openclaw.ai）系は身体ではなく**頭脳**——model-agnostic なエージェント・ランタイムで、CLI / API で外から叩ける。物理スタックチャン出力が実機を要するのと違い、この連携は**ソフトだけで完結する**。到達点を「向き」と「実装」の二段で記録する。

**向きと委譲**：向きは **3（佇か＝指揮役、頭脳に投げて返りをキャラで返す＝当初の意図）**、委譲は **soft（情報だけ）**。向き1（佇か＝アバター front-end）は佇か自身の人格が薄まるので採らない。soft に絞るのは §1「操作主体にしない」を守るため——ただし佇かの自制ではなく**構造**で担保する。

**実装：soft の現実的な範囲は、新ランタイムを足さずに閉じる。** 三つの理由：

1. **佇かは既に LLM に繋がってる**（`persona-llm`：ollama / Claude API）。知識で答えられることは生成すら要らない。
2. **生成 ≠ 実行。** 「何を見るか」を LLM に生成させるのはタダで安全。だが*生成された shell を実行する口*を持った瞬間、injection か幻覚一発で hard 側に滑る。soft を「約束」でなく「構造」で守るとは、**この実行口を作らない**こと。
3. **マスコットに効くローカル観察は知れた数。** 「まだ PR をレビューしてない」「ビルドがこけてる」「そのファイル開きっぱなし」——*こちらが書いた readonly プローブ*で届く。open-ended 探索が増やすのは茶々の量より**リスクと機械**。

だから soft の第一実装は **既存LLM＋ curated readonly プローブ**＝ §6-4 の**入力イベント源パターンそのもの**。佇かが「家の中も少し（readonly で）見えてる同居人」になる経路は、新しい契約ではなく**既存の蛇口を増やす**こと（[connectors/README.md](connectors/README.md) §3-1）。形としては向き2（賢い反応）に寄るが、下記 seam が共通なので**向き3 を foreclose しない**。向き2（出来事を situation に翻訳）も同じ蛇口に内包される。

**open-ended が要るなら（後段・同一 seam）**：将来「何でも自分で調べに行く部下」が本当に欲しくなったら、外向きの `delegate(query) → text` を足す。戻り値の落とし所は入力と同じ（結果が `situation` の ctx）で protocol 不変。頭脳には **ReadOnly のサブエージェント**を据える——第一候補は**自作 PawAgent に ReadOnly autonomy 段＋構造化出力を足したもの**（sibling リポ・shell/fs/gui/dbus を持つ hard エージェントだが、パス展開・コマンド解析・blocklist・HITL の安全足場が既にある）。サードパーティの ZeroClaw（依存ゼロ思想に逆らう外部ランタイム）や Moltworker より「中身を把握した自前」を優先する。ReadOnly 段が soft の境界で、autonomy を上げる＝§1 を意識的に上書きする hard 化＝**意図的スイッチ**。PawAgent 自身の原則「actuation は必ず HITL」とも噛む——*いじらないなら確認するものが無い*から ReadOnly だけは自律でよい。

**受動の口（ユーザーが佇かに話しかける）は別作業**：ユーザー→佇かのテキスト入力路は protocol の新語彙で、両側同セッションで直す独立した決定。`delegate()` の seam は能動でも受動でも同じものを使う。

土台は**既存の仲介ハブ（`server/hub.js`）がそのまま使える**。

## 8. 作業規律（重要）

- **`protocol/` が server と client の契約。** プロトコル変更は必ず両側を同じセッションで直す。片側だけのその場調整は禁止。
- **client は server が静的配信する。** オリジン一つ・HTTPS 終端一箇所。表示端末は「URL を開くだけ」。
- **改名禁止：** 将来 systemd user サービス化するので、リポジトリ名 `tatazuka` と `server/` のパスは変えない。
- ドキュメンテーション（protocol 仕様を含む）を先に書き、コードはそれを写す形で進める。
