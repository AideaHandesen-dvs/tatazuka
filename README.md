# 佇か（たたずか）

> 伺（うかが）かの精神的後継デスクトップマスコット。
> Linux デスクトップ透過の沼を**捨て**、表示をブラウザ端末（スマホ・タブレット・余った端末）に逃がす。
> 端末のバックカメラを背景に流し、傾けると覗き込める——**「透明な箱の中に佇かがいる」**。

「佇む」から。静かにそこに居て、ときどき茶々を入れてくる存在。

## クイックスタート

依存パッケージは無い（`npm install` 不要）。要るのは Node.js と、HTTPS のための証明書だけ。

```sh
# 1) 証明書（初回だけ）。getUserMedia / DeviceOrientation は HTTPS 必須なので要る。
#    <LAN-IP> は表示端末から届くこのマシンの IP（例 192.168.1.99）。
mkcert -install
mkcert -cert-file server/certs/cert.pem -key-file server/certs/key.pem \
  "$(hostname)" localhost 127.0.0.1 <LAN-IP>

# 2) 起動（HTTPS 静的配信 ＋ WebSocket。依存ゼロ）
node server/serve.js

# 3) 表示端末（スマホ等）のブラウザで開く
#    → https://<LAN-IP>:8443/?label=好きな名前
```

- **表示端末に mkcert の root CA を信頼させる**初回作業が要る（iOS / Android で手順が違う）。→ [server/README.md](server/README.md)
- **VRM アバターを出すには** `.vrm` を `client/models/` に置く（無ければ CSS の簡易顔になる）。→ [client/README.md](client/README.md)

## アーキテクチャ

```
表示クライアント（ブラウザ / どんな端末でも）          client/
  ├ getUserMedia      → バックカメラを背景に（端末の透過演出）
  ├ DeviceOrientation → 傾きで視点を動かす（覗き込める奥行き）
  ├ 顔を描く（WebGL 端末は VRM / それ以外は CSS の簡易顔）
  └ WebSocket で本体と繋がる
        ▲
        │ protocol/ ＝ 両者の契約（WS メッセージ仕様）
        ▼

  ├ WebSocket サーバー（RFC6455 自前実装・依存ゼロ）
  └ client/ を静的配信（オリジン一つ・HTTPS 終端一箇所）
        ▲
        │ （将来）
        ▼
OpenCLAW / 物理スタックチャン 等                       connectors/
```

# 設計の記録（なぜこの形か）

> ここから下は「育てていく設計メモ」。確定仕様ではなく、議論の到達点と**なぜそう決めたか**の記録。
> 設計の全体像はここを参照する（CLAUDE.md の規約）。

## 1. コンセプト

伺かの精神的後継。デスクトップに常駐し、人格を持ち、こちらに茶々を入れてくる存在。
ただし伺か本家の弱点（特に Linux での表示）を、アーキテクチャの根本的な見直しで回避する。

- デスクトップを動き回って仕事を邪魔してくる存在。
- ただし**今は**デスクトップを操作する機能は持たせない（操作主体だと誤解されない設計にしたい）。
- OpenCLAW インターフェース（スタックチャン的なもの）と接続しても楽しそう。

## 2. 最大の技術的課題：Linux での透過表示 → 諦めた

デスクトップに直接マスコットを住まわせる場合、Linux では背景透過が沼になる。

- **X11 か Wayland か**でまず分岐する。Wayland では「ウィンドウを好きな位置に置く・最前面固定・クリックスルー」というマスコットに必須の操作が、プロトコル上できない／コンポジタ独自拡張頼みになる。
- 透過自体が「コンポジタが合成してくれているか」に依存する。軽量 WM・コンポジタ無効環境では背景が真っ黒になる。
- Java（Swing/JavaFX）等で書いても、per-pixel 透過は環境差をモロに食らう。「書けるけど環境によっては透過しない」という一番タチの悪い状態になる。
- ディストリビューション対応・他 OS 対応を進めるほど、この環境差が増える。

**結論：デスクトップに直接住まわせるのを諦める。** 表示を別の場所に逃がすことで、透過・コンポジタ・WM の問題が**すべて関係なくなる**。これは妥協ではなく上位互換である（次節）。

## 3. 採用した方針：表示をスマホ／タブレットに逃がす

本体（佇かの「頭脳」）は Linux 上のサーバープロセスとして動かし、表示はブラウザを持つ別端末が担当する。両者は WebSocket で繋ぐ。これが上位互換になる理由：

### 3-1. バックカメラによる「端末そのものの透過」

スマホ／タブレットのバックカメラ映像を表示の背面に流すと、**端末そのものが透明になったように見える**。AR 的な「窓」になる。

- デスクトップ透過は「背景を消す」ことしかできないが、これは端末越しに机が見える状態を作れる。
- 佇かが本当に机の上に立っているように見える。端末を動かせば視差で背景がズレるので実在感が出る。
- ブラウザの `getUserMedia` で撮れるので実装も標準的。

### 3-2. 表示先は「ブラウザが動けば何でもいい」

軽く・枯れた技術で表示クライアントを作れば、性能の低い端末でも住処にできる。
**中古の学習タブレット（チャレンジタッチ・スマイルゼミ等、数百〜数千円のジャンク）にすら表示可能**であることを、この設計の強みの証明にしたい。「どこにでも憑ける」のは伺かのゴーストらしさとも噛み合う。

> 補足（2026-06）：初代の「中古500円チャレンジタッチ」は市場から枯れたが、スマイルゼミのジャンク（相場2千円前後、公式の Android 化手順あり）が同じポジションにいる。**試金石は特定機種ではなく「数千円以下の中古学習タブレット」というクラス**。

### 3-3. 傾きセンサで奥行きを出す

スマホ・タブレットの傾きセンサ（IMU）を表示に反映すれば、どこで表示してもリッチになる。

- ブラウザの `DeviceOrientation`（α/β/γ）を視点に使う。端末を傾けると佇かを**見る角度が変わる**。
- バックカメラ背景も傾きで一緒に動かせば、**端末が透明な箱で、中に佇かが入っている**ように見える。
- スタックチャンに載せる場合は、IMU 傾きを「佇かが体を傾けた」表現に変換する逆向きの使い方もできる。

### 3-4. cap（能力）で設計し、機種で設計しない

protocol が知っていいのは「傾きが取れるか」「カメラがあるか」だけで、「iPad かどうか」ではない。デバイスは cap の束として扱う。

| 端末 | ポインタ | 傾き/加速度 | カメラ | GPU | 役割 |
|---|---|---|---|---|---|
| デスクトップブラウザ | マウス | ✗ | △ | ◎ | 開発基準・最低ラインの確認 |
| Android スマホ | タッチ | ✓ | ✓ | ○ | **VRM フル体験の主力** |
| iPad Air 2（iOS 12.5.8） | タッチ | ✓（要許可） | ✓ | △ | 古い端末の試金石（CSS 顔） |
| 中古学習タブレット（将来） | タッチ | ✗ | ✗ | ✗に近い | 最底辺の証明 |

入力は2種類に分かれ、protocol 上の扱いが違う：

- **ポインタ系（なでる・つつく・長押し）→ cap 交渉不要**。タッチでもマウスでも同じ。「なでなで」をタッチ端末の特権にしない。
- **センサ系（傾き・加速度・カメラ）→ cap 交渉が必要**。ハードの有無＋許可ゲートがあるため、接続時に名乗る。

加速度（`DeviceMotion`）は傾きと別の語彙。**デスクトップモニタはデカくて揺らさないから不要。タブレットは小さくて持って動かすから、読めば表現が広がる**（「揺らすな」と怒る佇か）。

cap の初期セット：`orientation` / `motion` / `camera` / `webgl`（ポインタは交渉不要なので含めない）。

## 4. 顔：軽量3D（VRM）を上位レイヤで

傾けて覗き込めるなら、重要なのはミニマル／リッチではなく**3D 的な見え方をするか**。軽量3D が、傾きセンサ・カメラ透過・低性能端末対応のすべてに効く。

採用形：**CSS の簡易な顔を「床」として常に持ち、WebGL が効く端末ではそこに VRM アバターを「格上げ」で載せる**。顔のレベルでもプログレッシブ・エンハンスメント（§5）。VRM は three.js + three-vrm を vendor 同梱（バンドラ不要・外部 CDN 非依存）。視線追従（覗き込むと目で見返す）入り。モデル（.vrm）は各自で `client/models/` に置く（git 管理外）。詳細は [client/README.md](client/README.md)。

→ 顔のデザインは差し替え可能。`client/face.js`（CSS）/ `client/face-vrm.js`（VRM）を入れ替えれば変わる。

## 5. プログレッシブ・エンハンスメント（背骨）

`DeviceOrientation` と `getUserMedia` は HTTPS 必須・iOS は明示許可が要る・古い端末はセンサや新しい JS が無い——という現実がある。だから**全端末でフル機能を前提にしない。使える機能だけが順に有効化される**設計にする。

- WebGL が効かない → CSS の簡易な顔
- 傾きが無い → 覗き込み無効
- カメラが無い → 背景は単色
- それでも → **佇かは出る**

この背骨は実装の隅々まで貫通している（cap 三値・顔の格上げ・人格層の LLM 後付け・iOS 12 対応）。

## 6. 仲介ハブ構想（connectors）

スタックチャンの本質は「顔（表示）」と「中身（制御）」が分離していて API 経由で動かせること。佇か本体を**仲介ハブ**にすれば、表示先を差し替え可能にできる。

```
OpenCLAW  ⇄  佇か本体  ⇄  表示クライアント（ブラウザ / 物理スタックチャン）
```

protocol の封筒を `{type, data}` に分離してあるのは、この「封筒を見て中身を開けずに転送する」ハブの仕事への先払い（[protocol/README.md](protocol/README.md) §2）。

## 7. 作業規律（重要）

- **`protocol/` が server と client の契約。** プロトコル変更は必ず両側を同じセッションで直す。片側だけのその場調整は禁止。
- **client は server が静的配信する。** オリジン一つ・HTTPS 終端一箇所。表示端末は「URL を開くだけ」。
- **改名禁止：** 将来 systemd user サービス化するので、リポジトリ名 `tatazuka` と `server/` のパスは変えない。
- ドキュメンテーション（protocol 仕様を含む）を先に書き、コードはそれを写す形で進める。
